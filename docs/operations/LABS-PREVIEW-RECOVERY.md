# Labs Run Preview — Recovery, Lifecycle and Reliability Plan

**Status:** Snapshot-quota root cause and non-persistent worker fix are present on `develop`; operational recovery guidance is maintained here.
**Updated:** 2026-11-10
**Scope:** Owner Studio `Run` action for HTML/CSS/JavaScript and React JSX/TSX experiments. Automatic gallery poster capture is independent and must never be part of the interactive Run path.

## 1. Incident summary

The screenshot's generic message ("The isolated Labs compiler could not start") hid a Vercel infrastructure error. The deployment runtime log for the failing request showed:

- Request: `POST /api/v1/admin/labs/sources/spotlight-dock/preview`
- Vercel Sandbox create response: HTTP 402
- Reason: Hobby plan snapshot-storage usage limit exceeded
- The owner UI received only the generic `COMPILER_START_FAILED` message.

The immediate cause was the Vercel Sandbox SDK's default lifecycle. Sandboxes are persistent by default. Stopping a sandbox automatically snapshots its filesystem. Labs created a fresh one-off sandbox for each Run, stopped it after preview failures or expiry, and never reused the automatically saved snapshot. That created many full-sized snapshots for temporary workspaces until snapshot storage was exhausted.

The failing request did not reach the HTML/React build or the preview iframe. The editor's source content was not the cause and was not modified.

## 2. Correct lifecycle decision

| Resource | Lifecycle | Persistence |
|---|---|---|
| Compiler base image/snapshot | Immutable, intentionally retained and referenced by environment configuration | Persistent |
| Owner Run worker | One sandbox per run; compile, start preview server, stop after expiry/cleanup | **Non-persistent** |
| Release build worker | One sandbox per exact source-version build; compile, upload immutable output, stop | **Non-persistent** |
| Published artifact | Immutable Vercel Blob files referenced by the published artifact record | Retained independently of sandbox |
| Preview run metadata | TTL record containing owner, experiment, run ID, source hash, URL and expiry | MongoDB TTL |
| Automatic poster | Captured only during release build, version/artifact-bound, never during Run or page request | Retained independently of sandbox |

**Mandatory rule:** Every disposable Labs worker created from the compiler base must pass `persistent: false` to `Sandbox.create()`. Do not rely on calling `stop()` to prevent a snapshot; with default persistence, stop creates one.

Do not use a new persistent named sandbox for each Run. Do not snapshot source code, build output, temporary dev-server files or user data after a Run. Do not add a per-run snapshot refresh strategy.

## 3. Implemented corrections

### 3.1 Snapshot quota root-cause fix

- `createCompilerSandbox()` now creates one-off owner-preview and release-build workers with `persistent: false`.
- The worker still boots from the exact configured, immutable compiler snapshot and keeps `networkPolicy: "deny-all"`.
- The active Preview compiler snapshot and its referenced base chain were preserved.
- Twenty-two unreferenced automatic snapshots generated by previous one-off runs were deleted after reviewing the current branch/global environment references. Approximately 7.8 GB of snapshot storage was reclaimed.
- Do not delete any snapshot referenced by an active `LABS_COMPILER_SNAPSHOT_ID` value or required compiler image/base chain.

### 3.2 Actionable operational errors

- HTTP 402 / snapshot storage quota is mapped to `COMPILER_SNAPSHOT_STORAGE_LIMIT`.
- The owner API returns an actionable message that distinguishes storage quota exhaustion from source/build errors.
- Keep distinct mappings for missing/expired snapshot (410), rate limit (429), compiler capacity/startup failure, input initialization failure, build failure, type-check failure and preview server startup failure.
- Do not return a generic `COMPILER_START_FAILED` when a specific infrastructure failure is known.
- Error responses must never include tokens, environment-variable values, session credentials or unrestricted upstream messages.

### 3.3 Preview message integrity

- The isolated preview bridge now includes the current `runId` in ready and console messages.
- The Studio accepts messages only from the current iframe window, exact preview origin and current run ID.
- A new Run unmounts the previous iframe before creating a replacement, so late events from an earlier run cannot mark a new run as ready.
- The bridge sends ready only after page load and two animation frames, and withholds ready when a startup error or unhandled rejection has already occurred.
- The iframe startup timeout is 30 seconds; retry remains explicit.

### 3.4 Poster capture isolation

Automatic poster capture is a release-build step only. It must not run when the owner presses Run. It must not add a Chromium dependency to the Run worker or delay iframe startup. Failure to capture a poster is non-blocking for both Run and publish; the public card can fall back to existing artwork.

## 4. Run request lifecycle

Current request contract:

1. Studio sends the unsaved editor file snapshot to the owner-only preview route.
2. The route authenticates the owner, checks same-origin mutation, validates file count/size/path/language and validates the experiment belongs to that owner.
3. The compiler starts a fresh, network-denied, non-persistent sandbox from the configured compiler snapshot.
4. The compiler creates the fixed input directory idempotently, writes only this run's input and executes the pinned compiler.
5. The compiler validates build exit code, manifest, build hash, output count/size and entry document.
6. The sandbox starts the static preview server on the exposed port. The server binds `0.0.0.0`, serves only the per-run path, denies traversal/hidden paths and exposes a no-store health endpoint.
7. The route polls the exact sandbox health endpoint with bounded request timeouts. If the server never becomes healthy, it returns `PREVIEW_START_FAILED` and stops the sandbox.
8. The route persists a run record with a random run ID, owner, experiment slug, source hash, sandbox name, preview URL and expiry.
9. The Studio mounts a fresh iframe on the separate sandbox origin. The runtime bridge relays bounded console entries and a run-scoped ready signal.
10. The preview session is stopped when it expires or when an explicit cleanup path is introduced. Stopping this worker does not create a snapshot because it is non-persistent.

**Important existing boundary:** owner preview remains a synchronous POST. Keep its Vercel function duration aligned with the worst-case compiler, server-start and health-check time. Before raising build complexity or supporting slower compilation, migrate to a 202 Accepted run-job flow with an owner-only status endpoint and bounded polling. Do not simply increase timeouts beyond the deployment plan limits.

## 5. Recovery procedure

When Run fails:

1. Read the request's Vercel function logs for the exact failure code and underlying status.
2. For HTTP 402, confirm all disposable Labs workers use `persistent: false`, list snapshots for the portfolio project, and find unreferenced automatic snapshots. Delete only snapshots confirmed not to be referenced by any environment or active named sandbox.
3. For HTTP 410, confirm the branch-scoped `LABS_COMPILER_SNAPSHOT_ID` points to a created snapshot and deploy a new Preview after changing the value.
4. For HTTP 429, return `COMPILER_BUSY` and allow a manual retry with a small backoff. Do not create a burst of automatic retries.
5. For build/type-check failure, return bounded diagnostics and leave the editor content unchanged.
6. For preview server/health failure, stop the failed sandbox, preserve diagnostics, and allow an explicit retry.
7. Verify the owner route, server health, iframe origin and run-scoped ready handshake before declaring the Run ready.

Never change or delete Production environment references during Preview recovery. Never silently update the configured compiler snapshot from a request handler.

## 6. Configuration and operations

- Keep `LABS_COMPILER_SNAPSHOT_ID` branch-scoped for the active Preview branch when different environments need different compiler snapshots.
- Record the compiler snapshot ID, creation date, toolchain package versions, architecture, region, and smoke-test result in the compiler snapshot release notes.
- Keep the snapshot storage budget healthy. Do not create a snapshot for each Run, release build, test, import, or preview request.
- Clean up any old automatic snapshots only after checking environment references and sandbox dependencies.
- Keep `region: "bom1"`, `resources: { vcpus: 2 }`, `networkPolicy: "deny-all"`, and a bounded worker timeout unless a tested resource decision changes.
- Keep Blob storage and Cloudinary secrets in the application server only; never pass them to user-authored source code or the compiler environment.

## 7. Verification matrix

| Scenario | Expected result |
|---|---|
| Valid React JSX project | Build succeeds, isolated iframe loads, run-scoped ready event arrives |
| Valid React TSX project | Type-check succeeds before bundling; iframe becomes ready |
| Valid standalone HTML/CSS/JS project | Original HTML mode runs without a React wrapper |
| Invalid import/type/entry | Bounded actionable diagnostic; previous editor content remains intact |
| Runtime exception before ready | Console error appears; ready is withheld; UI enters failed state |
| Old iframe sends late ready/console event | Ignored because its window or run ID is no longer current |
| Server health timeout | `PREVIEW_START_FAILED`; worker stopped; retry offered |
| HTTP 402 snapshot quota | `COMPILER_SNAPSHOT_STORAGE_LIMIT`; actionable infrastructure message |
| HTTP 410 snapshot expired/deleted | `COMPILER_SNAPSHOT_EXPIRED`; branch-scoped snapshot recovery guidance |
| HTTP 429 rate limit | `COMPILER_BUSY`; no uncontrolled retry storm |
| Stop/expiry of one-off Run worker | No new automatic snapshot is created |
| Release build succeeds | Immutable output saved; poster capture is attempted separately and non-blocking |
| Poster capture unavailable | Interactive Run still works; gallery uses existing artwork fallback |

### Required deployment QA before calling this complete

- Test React JSX, React TSX, standalone HTML and a real Motion/Tailwind experiment.
- Confirm iframe console and ready messages include the correct run ID.
- Run twice consecutively and verify the previous iframe cannot update the second run's status.
- Verify the Vercel snapshot list does not gain an automatic snapshot when a disposable Run sandbox stops.
- Check Vercel function logs for zero 402/410/429/500 errors during these tests.
- Verify production settings and published Labs experiences remain unchanged.

## 8. Follow-up hardening

These are separate from the immediate quota fix:

- Move preview execution to an asynchronous run/status API if build and health-check time begins to approach the Vercel function duration.
- Add a bounded stop endpoint and a scheduled cleanup for expired sandbox sessions. MongoDB TTL only removes run metadata; it does not stop a sandbox.
- Add a rate limit per owner and experiment to avoid accidental parallel sandbox creation.
- Add correlation IDs to the Run request, sandbox name, run record and server logs; never log source code or secrets.
- Add a compiler-image health check and snapshot-reference validator to deployment/operations QA.
- Keep gallery screenshot capture separate from Run and use a browser only in the release capture worker when that browser runtime is explicitly installed and pinned.

## 11. When Run stops working because a limit was reached

A failed Run does **not** automatically mean the experiment code is broken. It can be a compiler error, a preview-server error, a sandbox/provider limit, a Vercel Function timeout, or an account-level usage limit. Diagnose the failed request before changing source code or repeatedly pressing Run.

### 11.1 Current limits in this repository

These are the code-level limits currently configured on `develop`. They are not all Vercel account-plan quotas.

| Layer | Current configured limit | Meaning |
|---|---:|---|
| Owner preview API route | `maxDuration = 60` seconds | The synchronous HTTP request cannot run beyond this function duration. |
| Compiler command | `45_000` ms | The isolated build command has its own 45-second timeout. |
| Owner preview sandbox | `10 * 60 * 1000` ms (10 minutes) | One preview worker is short-lived. When it expires, that preview URL stops working; start a new Run. |
| Source files | Maximum 40 files | More files are rejected during validation. |
| One source file | 500 KB | A single larger file is rejected with `FILE_TOO_LARGE`. |
| Complete source snapshot | 1 MB | Larger total source content is rejected with `SNAPSHOT_TOO_LARGE`. |
| Preview request body | 1,100,000 bytes when a `Content-Length` header is present | Larger requests are rejected with `REQUEST_TOO_LARGE`. |
| Compiled output | Maximum 80 files and 15 MB | Larger build output is rejected; remove unused assets or reduce generated output. |

The 10-minute sandbox lifetime is **not** the API request timeout and is **not** a monthly quota. Similarly, the 45-second compiler-command timeout is not the Vercel Function duration. Changing one does not change the others.

### 11.2 Identify which limit or failure occurred

| What you see | What it usually means | Correct action |
|---|---|---|
| `COMPILER_SNAPSHOT_STORAGE_LIMIT` or upstream HTTP 402 | Snapshot storage quota was exceeded. This was the previously confirmed incident. | Confirm disposable workers still use `persistent: false`. Review the Vercel Sandbox snapshot list and remove only confirmed-unreferenced automatic snapshots. Preserve the active compiler snapshot and its base chain. If storage is still over quota, follow the Vercel usage/plan guidance or upgrade the plan. |
| `COMPILER_BUSY` or upstream HTTP 429 | The Sandbox provider is rate-limiting or temporarily busy. | Stop repeated clicks, wait briefly, then retry once. Do not add rapid automatic retries or parallel Run requests. |
| `COMPILER_SNAPSHOT_EXPIRED` or upstream HTTP 410 | The configured compiler snapshot is missing, expired, or deleted. | Check `LABS_COMPILER_SNAPSHOT_ID` in the **Preview** environment, confirm the referenced snapshot exists, then redeploy Preview. Do not change Production while fixing Preview. |
| Vercel function timeout / request ends close to 60 seconds | The synchronous owner-preview route reached its configured function-duration limit. | Check the function duration and logs. The route currently declares `maxDuration = 60`; verify the project's Fluid Compute setting and the plan's supported maximum before changing it. If builds regularly approach the limit, use the asynchronous job/status design described above. |
| `PREVIEW_START_FAILED` | Compilation may have succeeded, but the static preview server did not become healthy before the polling loop ended. | Inspect sandbox command and server logs. Verify port 3000, the per-run preview path, and the `/__health` response. Retry only after identifying the startup issue. |
| `REQUEST_TOO_LARGE`, `FILE_TOO_LARGE`, or `SNAPSHOT_TOO_LARGE` | A repository input-size guardrail was reached. This is not a Vercel storage quota. | Reduce large source files, remove unnecessary files, or split unused content out of the experiment. Stay within the limits in section 11.1. |
| `BUILD_OUTPUT_TOO_LARGE` or more than 80 output files | The compiled artifact exceeded the output guardrail. | Reduce bundled assets, remove unused dependencies/assets, and avoid embedding large media in the source bundle. |
| `BUILD_FAILED`, `TYPECHECK_FAILED`, `UNRESOLVED_IMPORT`, or another 400/422 validation/build error | The input or experiment code failed validation, type-checking, or compilation. | Read the bounded compiler diagnostic and fix the named file/import/type issue. Increasing plan limits will not fix a source error. |
| Preview iframe stops responding after about 10 minutes | The one-off sandbox reached its configured lifetime. | Press Run again to create a fresh preview. Do not recreate or refresh the compiler snapshot for this normal expiry. |
| Generic `COMPILER_START_FAILED` | The failure did not match one of the specific mapped provider errors. | Read the Vercel Function logs for the underlying Sandbox response/status and deployment. Do not assume it is a source-code error or snapshot quota without evidence. |

### 11.3 Check whether the Vercel account/team usage was exhausted

Use this path when several unrelated server actions fail, Vercel reports that the team/project is paused, or the request logs point to account usage rather than a Labs compiler error.

1. Open the Vercel team and the portfolio project.
2. Check the team's **Usage**, **Limits**, and **Spend Management/Billing** views. Inspect the specific meter reported by Vercel (for example, active CPU, provisioned memory, Function duration/invocations, or Sandbox-related storage/usage).
3. Check the period, current usage, limit, and next reset date shown for that meter. Do not assume every quota resets on the same schedule.
4. If the team or service is paused because an included allowance was exceeded, follow the action and reset guidance shown in Vercel. Depending on the meter, that may mean waiting for the allowance to reset or changing the plan. A snapshot-storage quota caused by retained snapshots is different: waiting alone does not remove those snapshots.
5. After the provider issue is resolved, run one fresh Preview test and confirm the route, sandbox health endpoint, and iframe ready handshake.

Vercel's plan and usage limits can change. Verify the current dashboard and official plan documentation instead of copying a historical quota number into application code.

### 11.4 Safe recovery sequence for the owner

1. Do not keep clicking Run while the first request is pending or failing. The current follow-up hardening list includes an owner-level rate limit; until that exists, run one preview at a time.
2. Keep the editor source intact. A provider quota, sandbox startup failure, or function timeout does not prove the source is invalid.
3. Open the matching Vercel Preview deployment's Function logs and filter for `POST /api/v1/admin/labs/sources/<slug>/preview`. Record the timestamp, HTTP status, application error code, request duration, and underlying Sandbox status.
4. Check the matching Sandbox logs/metrics if a worker was created. Confirm whether it started, whether the compiler command completed, whether the preview server listened on port 3000, and whether `/__health` returned successfully.
5. Apply only the recovery action for the identified category in section 11.2. Change environment variables only in the intended Preview environment, and redeploy when a snapshot/configuration change requires it.
6. Retry once. Confirm a new run ID, a healthy preview URL, and a ready message from the current iframe before considering the issue resolved.

### 11.5 Do not use these as blind fixes

- Do not delete the configured compiler snapshot, its base image, or any snapshot referenced by an active environment.
- Do not change Production environment variables while recovering a Preview deployment.
- Do not repeatedly press Run, run several previews in parallel, or add automatic retry loops for 402/429/provider errors.
- Do not increase `maxDuration` without checking the active Vercel compute mode and plan ceiling.
- Do not increase the sandbox timeout to solve a function timeout; those timers control different processes.
- Do not rewrite valid experiment code to resolve a confirmed platform quota or infrastructure failure.
- Do not connect poster-capture/Playwright work to the interactive Run request. Poster capture remains release-only.
